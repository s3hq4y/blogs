## 起点：一个矛盾的需求

我想做一个像 QQ 空间一样的东西：发文章，但每篇能单独控制"谁能看"。有的给所有人，有的只给好友，有的要口令，有的只有我自己。

听起来简单，但一旦落到"托管在 GitHub Pages 或 Cloudflare"这种静态方案上，就会撞上一个硬约束：

**静态托管的产物是公开的。任何被构建进 HTML 的内容，F12 一看就露。**

所以"用前端把它藏起来"根本不是访问控制，只是障眼法。真正的访问控制必须满足一个条件：**内容在到达浏览器之前就被拦下**。

## 方案：把守门人放在服务端

架构只有三层：

```
浏览器  →  Cloudflare Worker（守门人）  →  私有仓库
```

- 文章存在一个**私有仓库**里，只有 markdown
- 网站代码在另一个**公开仓库**里（Worker + 前端）
- Cloudflare Worker 持有读私有仓库的 token，在前端和仓库之间当唯一的门

关键在于：Worker 先验证访客身份，再决定"给不给他这篇文章的正文"。不给，正文压根不进入响应体。

## 完整链路：一次访问到底发生了什么

这是本文的重点。假设你在浏览器里访问 `https://space.s9y.workers.dev/api/posts/hello`。

### 第 0 段：文章怎么进入系统

1. 在本地 `posts/hello.md` 写文章，头部带 frontmatter
2. `git push` 到私有仓库
3. **没有构建步骤**。没有 CI 生成 HTML，没有预渲染

这是和传统静态博客最大的区别：文章不是"构建产物"，而是"数据源"。改权限、加口令、隐藏文章，都不需要重新构建部署。

### 第 1 段：请求到达 Worker

因为配置了 `run_worker_first = true`，Cloudflare 不会先用静态资源匹配，而是**先交给 Worker**。

> 这里有个坑：默认情况下 Cloudflare 会先返回匹配到的静态文件，只有没匹配才走 Worker。那样 `/api/*` 会被 SPA 回退成 `index.html`，鉴权直接失效。必须显式打开 `run_worker_first`。

### 第 2 段：Worker 识别访客

Worker 从 Cookie 里读会话（一个 HMAC 签名的 token），解出访客身份，得到三种之一：

- **站主** —— GitHub 用户名匹配 `SITE_OWNER_GITHUB`
- **好友** —— GitHub 用户名在 KV 白名单里
- **访客** —— 其他所有人

身份解析完，Worker 得到一个 `viewer` 对象。

### 第 3 段：Worker 去仓库取数据

Worker 用环境变量里的 `GITHUB_TOKEN` 调 GitHub API：

1. `GET /repos/.../git/trees/main?recursive=1` 拿到整个文件树
2. 筛出 `posts/*.md`
3. 对每个文件 `GET /repos/.../contents/<path>` 取原始内容

为了不每次都打 GitHub，列表结果在 Worker 内存里缓存 60 秒。

### 第 4 段：解析 + 过滤

对每篇 markdown：

1. 用 `js-yaml` 解析 `---` 之间的 frontmatter
2. `draft: true` 的直接丢弃
3. 读 `visibility` 字段，结合 `viewer` 身份判断这篇该不该给

这是整个系统的核心。一张表说清：

| visibility | 出现在列表 | 谁能读正文 |
| --- | --- | --- |
| `public` | 是 | 任何人 |
| `unlisted` | 否 | 知道链接的人 |
| `friends` | 是 | 好友 + 站主 |
| `password` | 是 | 口令正确者 + 站主 |
| `private` | 否 | 仅站主 |

注意 `unlisted`：它不出现在列表，但知道链接就能读——这就是"隐藏但可分享"。

### 第 5 段：返回

- 列表接口只返回**可见文章的元数据**（标题、日期、摘要），不返回正文
- 详情接口逐个鉴权，通过了才把渲染好的 HTML 放进响应

访客请求一篇 `friends` 文章，得到的是 `403`，响应体里没有正文；请求 `password` 文章，得到 `401`，前端弹出口令框。

## 两道身份轨道

好友不一定是开发者，所以登录做了两条轨：

- **A 轨 · GitHub OAuth** —— 有 GitHub 的好友，登录后用户名进白名单
- **B 轨 · 口令** —— 没 GitHub 的好友，给一个分享链接 + 文章口令

两轨最终都归一到 Worker 里的同一个 `viewer` 对象，权限判断只有一份逻辑。

## 几个设计取舍

**为什么不用数据库？**
因为文章的编辑体验，markdown + git 已经是最好的。版本、diff、回滚全都免费。

**为什么口令校验必须在服务端？**
如果在前端比对口令，口令本身就得先发到浏览器——那等于没有保护。现在口令存在 Cloudflare KV，只存在于服务端。

**为什么列表缓存 60 秒？**
GitHub API 有速率限制，每次列表都打一遍所有文件太浪费。代价是改了权限最多 1 分钟才生效。

## 小结

整条链路可以压缩成一句话：

> 文章是数据，不是产物；权限判断发生在服务端，正文只在该出现时才出现。

这套结构不依赖任何框架，没有运行时数据库，成本几乎为零（Cloudflare 免费额度足够），但拿到了真正的访问控制。对个人站点来说，这是"够用且正确"的平衡点。
